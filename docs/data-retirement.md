# 기기 공통 데이터·리포 퇴역 절차

`oracle` / `nuc` / `laptop` / `thinkpad` 공통 수동 운영 절차다. 캐시 청소와 별도로 **더 이상 쓰지 않는 데이터·백업·개발 사본의 수명**을 관리한다. 동일한 폴더 구조라도 크기·마운트·활성 참조·독립 사본은 기기마다 다시 확인한다.

이 문서는 삭제 허가나 자동 보존기간을 부여하지 않는다. 보존 세대/일수·외부 저장소·최소 사본 수는 자산별 결정 사항이다. 자동 삭제·cron·숨은 이관은 만들지 않는다. Oracle 재부팅 정본은 [oracle-reboot 스킬](../.claude/skills/oracle-reboot/SKILL.md), 일반 캐시/GC 정리는 [AGENTS.md §2.6](../AGENTS.md)와 `scripts/diskclean.sh`다. 부분 데이터 승인으로 전체 safe/deep을 실행하지 않는다.

## 1. 실측 — 리포 이름보다 무엇이 공간을 쓰는가

- 디바이스·KST·실제 파일시스템과 `df` 사용자 가용 바이트를 기록한다. root와 home을 구분한다.
- `$HOME/repos/<group>/<repo>`별 합계와 `.git`, 데이터, `node_modules`/`.venv`, 빌드 출력, `.tmp-verify`, `.agent-reports` 등을 나눠 본다. Git 마커 없는 데이터 폴더도 별도로 표시한다.
- 심볼릭 링크는 별칭과 실제 경로를 기록하며 무심코 따라가지 않는다. 같은 inode·공유 pnpm store·Git alternates·중첩 디렉터리를 독립 회수량으로 더하지 않는다. `.git` 합계도 전부 오래된 이력은 아니다.
- 긴 수집은 기본 소켓의 보이는 tmux. 비공개 영수증은 Git 제외 디렉터리700/파일600. 출력은 화면에도 남긴다.
- 메타데이터 우선: 경로·할당 크기·mtime·버전 표시·소유자·참조. 권한 거절은 범위 누락으로 기록하며 sudo로 확장하지 않는다. auth/env/개인 세션 본문을 덤프하지 않는다. 원격 URL의 사용자정보·토큰·query를 기록하지 않는다.

판단 행은 `기기·실경로/별칭 / 크기·주원인 / Git·worktree 상태 / 미푸시·미커밋·ignored / LFS·annex 및 콘텐츠 위치 / 원본성 / 활성·차용 참조와 검사 범위 / 재생성·복구 출처 / 제안 / 승인 상태`다. 아직 조사하지 않은 열은 미확인으로 남긴다. mtime은 마지막 사용 시각이 아니며, 이름의 `bak`/`tmp`/`archive`는 중복·폐기 가능성의 증거가 아니다.

### 읽기전용 재측정 예시

아래는 삭제 명령이 아니라 메타데이터 관측이다. 긴 수집은 보이는 tmux에서 하고 출력/오류는 해당 기기의 비공개 영수증에 함께 남긴다. 전체 home/auth/세션 본문으로 범위를 확대하지 않는다.

```bash
umask 077
# 사람에게 실제 사용 가능한 바이트; root와 home이 다른 FS인지도 확인
df -B1 / "$HOME"
# 리포별 + 바로 아래 구성. symlink/다른 FS를 따라가지 않는 경로 귀속 크기
gdu --config-file /dev/null -n -p -c -x --max-cores 2 --depth 3 \
	--no-delete --no-view-file --no-spawn-shell "$HOME/repos"
```

`--config-file /dev/null`은 개인 gdu 설정의 DB 저장·archive browsing·기타 옵션이 관측 범위를 바꾸지 않게 한다. 읽기전용 명령도 누락/권한 오류를 보고하고 범위를 적어야 한다. 합의한 후보의 `stat` UID/모드/mtime과, 공유 의심 파일의 `(device,inode,nlink,blocks)`를 따로 비교한다. root 소유·읽기전용·하드링크·독립 사본은 서로 다른 속성이다. 가용 바이트를 실제 동작 전후에 다시 기록하며 단일 경로 합계를 회수량으로 바꾸지 않는다.

### 수동 검토 영수증의 최소 항목

Oracle 재부팅 검토의 `storage-review.md`도 이 형식을 쓴다. 체크리스트 작성은 자동 승인이 아니다. 미수행·미관측은 ‘미확인/보류’, 실행하지 않기로 한 명시적 선택은 ‘변경 없음’으로 구분해 적는다.

```text
기기·KST·리포 SHA / 사용한 정본 소스 해시:
검사한 루트·별칭·다른 FS / 관측 누락·오류:
root/home 사용자 가용 바이트 전후 / 목표와 작업 피크 예산:
후보별 경로·귀속 크기·원본/재생성/복구 분류·UID/모드·공유/활성 참조:
코드 SHA/원격·로컬 전용 작업·LFS/annex / 별도 데이터·사본·복원 검증:
provider·계정·heartbeat·cron의 운영 중지 상태와 유지/변경 범위:
GLG의 정확한 실행 승인 / 보류·변경 없음과 그 이유:
명령·exit·실제 결과·오류/회복 / 모델 호출 여부:
최소 증거의 내구 문서 / 원시 로그·사본 보존/퇴역 판단:
다음 한 수 / 권한·용량·데이터 결정이 필요한 항목:
```

## 2. GLG가 고르는 퇴역 모드

| 모드 | 적용 조건과 남길 것 |
|---|---|
| **상주** | 현재 서비스·개발·조회에 필요. 데이터와 필요한 실행 의존성 보존 |
| **영구 폐기** | 원본/복구점 자체도 더 보존하지 않겠다고 GLG가 명시 선택. 재생성 불가 여부와 정확한 범위를 기록하고, 불필요한 안전 사본을 새로 만들지 않음 |
| **재생성물 회수** | 닫힌 검증 사본·빌드 출력·의존성 등. 재생성 입력과 공유/활성 참조를 확인하고 승인된 집합만 회수 |
| **로컬 얕은 사본** | Git 이력이 주원인이고 기존 로컬 전용 작업이 없음. 기본 브랜치 최신 사본 등 필요한 범위를 결정. 원격 이력을 다시 쓰거나 force-push하지 않음 |
| **콜드 이관** | 원본·대용량 데이터는 필요하지만 이 기기에 상주할 필요 없음. 목적지 복사·일관성·무결성·독립 사본 확인 후에만 원본 은퇴 |
| **README만 유지** | 코드 원본과 필요한 데이터의 재취득 경로가 검증됨. 같은 이름의 작은 디렉터리에 퇴역 사유·기준 SHA/브랜치·복원 경로를 남김 |

GitHub에 코드가 있다는 사실은 ignored 파일·LFS/annex 콘텐츠·DB·사진·세션·미푸시 작업의 백업이 있다는 뜻이 아니다. Git 마커 없음은 연결된 worktree·깨진 Git 디렉터리도 포함할 수 있으므로 데이터 폴더라고 단정하지 않는다. 어느 경우든 출처 확인 없이 ‘GitHub에서 다시 받으면 됨’을 적용하지 않는다. 심볼릭 링크 별칭 자체에 얕은 사본/README-only를 적용하지 말고, 실제 대상과 그 기기 한정 범위를 따로 승인받는다.

## 3. 리포를 비우기 전 확인

1. 가장 가까운 `AGENTS.md`와 소유자 절차를 읽는다. 현재 작업·코디네이터·서비스 의존성을 확인한다.
2. 현재 브랜치/SHA, 로컬 브랜치·stash·worktree, tracked 변경, untracked/ignored 데이터의 존재와 보존 의도를 확인한다. 패치/개인 본문을 광역 덤프하지 않는다.
3. 원격 출처와 필요한 커밋·콘텐츠가 실제로 복구 가능한지 확인한다. 오래된 로컬 remote-tracking ref만으로 ‘전부 푸시됨’을 보장하지 않는다. 얕은 사본은 로컬 교체만이며 원격 객체를 줄이지 않는다. 이 절차는 어떤 push도 허가하지 않으며 특히 mirror push로 원격 ref를 삭제하지 않는다. 로컬 전용 ref의 폐기는 별도 확인한다.
4. 프로세스 cwd/exe/fd, 전용 마운트, 실행 경로·심볼릭 링크, Git common-dir/alternates 및 공유 객체의 차용 관계를 확인한다. 발견하지 못한 참조와 ‘참조 없음’을 구분한다. 검사한 루트/항목 수·발견한 참조 파일 수·차단 참조 수·미관측/오류를 분리해 기록한다. ‘발견한 alternates 파일0개’를 ‘모든 참조를 검사했고0개’로 바꾸어 말하지 않는다. 쓰기 중인 DB는 소유자 도구의 일관된 export/backup 절차가 필요하다.
5. 임시 이관·얕은 재clone에도 여유 공간이 필요하다. 새 사본 검증 전 기존 유일 원본을 먼저 지우는 방식으로 공간 문제를 해결하지 않는다.

## 4. 에이전트 작업 잔여물 — 생성한 쪽이 마무리한다

`.tmp-verify`와 `.agent-reports`를 무기한 보관함으로 쓰지 않는다. 만들 때부터 **작업/소유자, 재생성 입력, 종료 조건, 보존 또는 폐기 판단 시점**을 함께 둔다.

- **진행 중:** 실행 코드·열린 작업·미결 장애/리뷰·핸드오프가 참조하는 파일은 보호한다.
- **닫힌 재생성물:** 샌드박스·검증 clone·빌드 결과는 입력 SHA/lockfile/절차와 차용 관계를 확인해 퇴역 후보로 묶는다. cwd/fd/실행·차용 관계가 미측정이면 ‘닫힌 재생성물’이 아니라 미확인 후보로 남긴다. 생성 세션이 사라졌다는 이유만으로 폐기하지 않는다.
- **닫힌 증거:** 필요한 결론·핵심 출력·버전/SHA·복구 경로를 내구 문서에 승격한다. 모든 원시 로그와 중복 소스 사본을 영구 보존하는 것이 기본은 아니다. 유일한 원본/증거인지 먼저 구분한다.
- **집합 승인:** 정확한 경로 목록·제외 조건·크기·분류를 고정해 한 묶음으로 승인받는다. 승인 뒤 새로 생긴 파일/디렉터리로 glob 범위를 확대하지 않는다.
- 완료 시 생성자가 잔여물과 회수/보존 이유를 보고한다. 다른 레인의 산출물은 소유·진행 상태를 확인한다. ‘모르므로 영원히 보존’ 대신 미확인 항목과 필요한 결정을 남긴다.

## 5. OpenClaw 복구 사본 — Oracle에서만

- 현재 DB/config/auth·세션·WAL과 복구용 사본을 분리한다. `.bak` 이름만 보고 활성 DB나 유일 원본을 지우지 않는다. 민감한 사본을 공개 Git/README에 넣지 않는다.
- 전체 cold archive, 특정 버전 컷오버 사본, 개별 DB migration backup, config 회전본, 바이너리 교체 사본을 따로 집계한다. 백업 파일 개수와 독립 복구점 개수는 다르다. cold tar 한 파일과 그 파일이 든 전체 디렉터리도 다른 승인 범위다. config 옆 bak·cold tar·swap 영수증·인증 사본은 서로 다른 자산 단위로 제시하고, 공개 결정표의 인증 사본은 부모 경로·개수만 표시한다.
- 각 복구점은 버전/이미지·스키마·시점·범위·복원 검증 여부를 연결한다. 파일명은 단서일 뿐 복원 검증이 아니다. 새 버전의 DB를 옛 이미지로만 돌려 복구할 수 있다고 가정하지 않는다.
- 보존할 복구점을 GLG가 고르고 나머지 정확한 사본 집합을 은퇴한다. 보존 사본을 실제로 검증하지 않았다면 ‘미검증’으로 남긴다. 정리 승인을 버전업·서비스 중단·이미지 prune 승인으로 확대하지 않는다.

## 6. 실행과 영수증

`고정 후보 목록 → GLG 범위 승인 → 직전 경로/참조 재확인 → 승인 동작 → 경로 상태·실제 가용 바이트 확인` 순서다. 정책/모드 선택과 실제 대상 집합 실행 승인은 구분한다. 보존 세대/일수가 미정이면 임의의 OpenClaw 기본 폐기 세대를 배정하지 않는다. 명령 실패/부분 완료를 기록하고 맹목 재시도하지 않는다. 후보 크기와 실제 `df` 증가를 구분하며 주기마다 같은 양이 회수된다고 보장하지 않는다.

README만 남길 때 최소 필드:

```text
상태: 로컬 사본 퇴역 / 복원 전 작업 금지
퇴역일·기기·사유: <date / device / reason>
원본 출처: <credential-free URL>
기준: <branch/tag/commit>
별도 데이터: <복구 위치·보존 범위 또는 없음>
복원 방법: <기존 README 디렉터리와 충돌하지 않는 복원 경로/절차>
검증: <푸시·독립 사본/콘텐츠 확인 근거, 미확인은 명시>
```

‘이관·복구 가능하게 보존’과 ‘더 필요 없어 영구 폐기’는 다른 결정이다. 유일 사본이라는 이유로 GLG가 명시한 폐기를 영원히 막거나 같은 삭제 승인을 반복해 묻지 않는다. 반대로 코드 재취득 가능성만으로 원본 데이터 폐기까지 추정하지 않는다.

`git-annex` 설치는 이관 자체가 아니다. 실제 도입은 첫 데이터 묶음·리포 경계/공개 여부·목적지·최소 독립 사본 수를 정한 뒤 별도 승인한다. 로컬 drop 뒤에도 정한 최소 사본 수가 서로 독립적인 장치/손실 영역에 남아야 한다. 지울 로컬 사본을 포함해 개수만 채우거나 같은 디스크의 두 폴더를 독립 사본으로 세지 않는다. 필요한 사본의 실제 존재·무결성을 확인한 다음에만 drop한다. `--force`나 원격 이름만으로 유일 사본을 지우지 않는다. 회사 계정의 저장소를 퇴사 후에도 남을 유일한 원본 보관처로 삼지 않는다.

## 7. 스토리지 예산 초과 — 권고 → 담당 리포 대응 → 필요시 방 비우기

원본/기억/연구 데이터라는 이유가 무제한 로컬 저장 허가는 아니다. 운영자는 기기 전체의 가용 공간과 리포별 상주·작업 피크 예산을 관리한다. 수치가 아직 합의되지 않았다면 담당 리포가 예산과 축소안을 제출하게 하며, 현저한 용량 압박을 단순한 기능 개선 제안으로 미루지 않는다. 모든 리포에 적용할 고정 GiB 한도나 자동 퇴거 타이머를 임의로 만들지는 않는다.

1. **측정·권고:** 경로별 할당 크기와 주원인, 가용 공간 영향을 측정하고 담당 리포에 이슈/권고를 남긴다. 외부에서도 읽을 수 있도록 결정적 집계 줄을 붙이되 개인 경로·코퍼스·인증 파일 본문은 싣지 않는다. 에이전트 작성 관점과 GLG 직접 발화가 아님을 맨 위에 표시한다.
2. **역할 분리:** 운영자는 ‘이 서버에서 이 용량을 감당할 수 없으니 줄이거나 배치를 바꿔라’고 요구한다. 내부 알고리즘·기억축·인덱스/모델을 대신 설계하지 않는다. 담당 리포가 관련 로직 소유자와 논의해 축소 방법·정상/피크 예산·회수와 재증가 방지 절차를 제안한다.
3. **선택:** GLG가 축소 / 상주 범위 축소·이관 / 로컬 퇴역 중 고른다. 권고 이슈는 코드 변경·유료 재생성·데이터 삭제·업로드 승인이 아니다.
4. **퇴역:** 축소로 예산을 맞추기 어렵거나 여기서 쓰지 않는 리포는 §3 검증 후 승인 범위를 비우고 README로 방을 비웠음을 남긴다. GitHub에 없는 로컬 정본이 발견되면 그 항목만 예외로 기록해 별도 폐기/이관 결정을 받는다. 리포 전체를 무기한 붙들거나 유일 자료를 조용히 없애지 않는다.
5. **다시 측정:** 실행 뒤 실제 가용 바이트와 남긴 예외를 기록한다. 폐기된 복구 사본을 가리키는 운영 문서도 고쳐, 존재하지 않는 백업을 다음 운영자가 믿지 않게 한다.

세션 코퍼스처럼 다른 프로그램이 직접 읽는 데이터의 annex 도입도 저장 운영 작업이다. 코드 리포와 데이터 보관 경계, 현재 읽기 경로·매니페스트·증분 수집 호환성은 해당 소유자와 확인한다. 패키지 선언이나 ‘적용 대상’ 선택을 init/add/drop 실행으로 확대하지 않는다.

## 8. 지워지지 않는 폴더 — root 소유와 읽기 전용을 구분

- 최상위와 하위 항목의 UID/GID·디렉터리 쓰기/탐색 비트·심볼릭 링크/마운트·ACL/immutable 등 관측 범위를 구분해 기록한다. ‘rm 실패’만으로 root 소유나 관리자 권한 필요를 단정하지 않는다.
- 사용자 소유 디렉터리도 쓰기 비트가 없으면 내부 항목 삭제가 막힌다. 반대로 root 소유 파일도 부모 디렉터리에 필요한 쓰기/탐색 권한이 있으면 unlink 가능한 경우가 있다. 파일 모드와 부모 디렉터리 권한은 다른 질문이다.
- Go module cache 같은 의도적 읽기 전용 재생성물과, SDK 업그레이드 전 동결한 대화 DB 사본은 다르다. 이름에 SDK가 있다고 패키지 캐시로 분류하지 않는다. `session.sqlite`와 WAL/SHM은 한 보존 단위이며, 내용/원본성을 확인하지 않은 DB를 재현 가능한 캐시로 취급하지 않는다.
- 삭제/권한 변경은 별도 범위 승인 뒤 해당 소유자 절차로 한다. 사용자 소유라는 이유로 재귀 chmod/chown을 먼저 하지 않는다. 공유 하드링크·심볼릭 링크 대상·실행 코드·동결 백업에 영향을 줄 수 있다.
- `sudo -n -ll`은 현재 허용 목록을 읽는 수단이지 삭제 실행이 아니다. 인증 없는 특정 명령만 허용됐다고 일반 sudo가 허용된 것은 아니다. 필요한 관리자 명령이 없으면 정확한 작업을 GLG에게 요청하고, 허용된 다른 실행 파일을 이용해 root 셸이나 우회 삭제를 만들지 않는다.
- 프로세스/FD 참조 미관측은 미사용 증명이 아니다. 코드·설정의 경로 참조와 스킬/실행 링크도 함께 본다. 생성자가 종료 때 의도적으로 남긴 검증 샌드박스는 그 보존 이유와 종료 상태를 확인해 퇴역 후보로 관리한다.

## 9. 공유 패키지·runtime tmp·진단 DB

`S`/shared 표시가 있으면 `(st_dev, st_ino)`로 실제 공유 파일을 확인한다. 두 경로의 크기를 더하지 않으며, 어느 한쪽만 지울 때 마지막 링크가 아닌 파일은 회수되지 않는다. `tmp`가 거대해 보여도 대부분 다른 패키지 트리와 공유한 실행 바이너리라면 독자 회수량은 매우 작을 수 있다.

플러그인 캐시/캡처, 실행 shim, 잠금 파일은 이름이 tmp이거나 크기0이어도 활성 런타임 일부일 수 있다. 설치 메타데이터·실효 enabled/status·원본/캡처 공유 관계·CLI 실행 경로와 관측 참조를 확인한다. 비활성 선택 플러그인도 공유 SDK/의존성 관계를 확인한 후 소유자 제거 절차로 다루며, 일부가 비활성이라고 전체 node_modules나 전역 플러그인 디렉터리를 지우지 않는다.

SQLite도 역할을 나눈다: 활성 대화/기억 원본, 과거 import 원문 보관함, CLI 진단 로그는 서로 다른 자산이다. 로그 정리 승인을 대화 DB 삭제로 확대하지 않는다. 마지막 수정 시각과 관측 참조는 단서이며 미사용 증명이 아니다. 허용된 정리도 DB/WAL/SHM 단위와 writer 상태를 확인하고 수행하며, 읽기전용 용량 조사 중 DB를 열어 checkpoint/vacuum하거나 원문을 조회하지 않는다. 보존할 원본/복구점의 가치는 로직 소유자·GLG가 결정한다.

## 10. Provider 운영 정지와 시간초과 후 마무리

- 예산/가용성 정지는 provider의 실제 ID·설정 스키마·primary/fallback·heartbeat·cron을 메타데이터로 확인하고 적용한다. 다른 유료 모델이나 API 키로 몰래 대체하지 않는다. 정지 provider만 쓰는 봇의 입력/자동 실행도 필요 범위에서 멈추며 원래 모델·기록·인증은 별도로 보존한다. 달력에 따른 자동 재개나 doctor의 재활성화를 만들지 않는다.
- 설정 변경은 네이티브 dry-run/배치 기능을 우선 사용한다. 필요한 일시적 설정 백업은 비공개600으로 만들고, 성공 검증 뒤 승인된 불필요 사본은 회수한다. 실패 상태에서는 복구 사본을 먼저 없애거나 provider를 자동으로 다시 켜지 않는다.
- 서비스 중단이 필요하면 실제 ready/activeCount0/blockers[]·남은 TTL을 검증하고 예산 안에서 수행한다. 강제 활성 턴 중단·반복 restart·이미지 교체를 묶지 않는다. 검사에는 모델 turn 대신 plugin enabled/status·설정 leaf·RPC health·공개면을 사용한다.
- Docker exec 클라이언트 시간초과는 컨테이너 안 작업의 미실행/중단 증명이 아니다. 해당 실행의 식별·잔여 프로세스·설치 기록·파일 상태를 측정해 완료/부분 완료를 구분한다. 이미 완료된 uninstall/config 동작을 다시 실행해 성공 표시를 만들지 않는다.
- 건강 검사 대기시간 초과도 추가 재시작의 허가가 아니다. 실제 현재 상태가 나중에 healthy로 확인되면 읽기전용 검증으로 이어가고, 실패 영수증을 성공으로 덮어쓰지 않는다. 재시작 구간의 오류·서비스 영향·회복·미해결 원인은 분리해 남긴다.
- 재개는 새로운 GLG 승인으로 한다. 정지 동안 정리한 의존성/설치 상태를 먼저 확인하고 provider 가용성을 검증한 뒤 해당 입력/자동화를 복원한다. 저장된 primary 이름이나 과거 성공 기록만으로 호출을 재개하지 않는다.
