# 추가 사용자 — 비활성 설계

`lib/mksystem.nix`의 `user`는 기존 운영자다. `additionalUsers`는 기본값이 빈 attrset이며 각 항목은 `osModule`과 `homeModule`을 받는다. `lib/additional-user.nix`는 계정명과 Home Manager stateVersion을 명시하는 최소 모듈 쌍이다. 어떤 실제 프로필에도 추가하지 않았다. 실행 가능한 평가 예시는 `tests/additional-users.nix`에 있다.

이것은 **계정 추가**이지 운영자 교체·인계 절차가 아니다. 시스템 모듈은 여전히 기존 운영자를 참조한다: `machines/shared.nix`의 Nix trusted-users, 암호 없는 wheel sudo와 운영자 sudo 규칙, 운영자 소유 Syncthing이 그 예다. 따라서 추가 계정에 wheel을 주면 기존 정책상 암호 없는 sudo를 얻는다. Nix trust는 root 권한에 준하므로 별도 결정이다. 추가 계정은 기본적으로 wheel, trust, 동기화, 개인 앱·인증을 받지 않는다. 다른 모듈의 그룹 부여나 시스템 전체 정책은 별도로 감사해야 한다.

운영자 교체는 별도 설계와 승인 대상이다. 하드코딩된 사용자·홈·UID, 서비스 소유권, SSH/인증, sudo와 Nix trust, Syncthing의 동기화 전파 및 백업/복원·롤백 세대까지 확인해야 한다. 계정 삭제나 파일 이동은 이 모듈의 기능이 아니다. 실제 적용 전 로그인·sudo·데이터 격리와 복구를 검증한다. 인증정보는 복사하지 않는다.

## 인계에서 일반화할 범위

- **전용 앱·tmux**: 사용자별 Home Manager 모듈에 담을 수 있다. 브라우저·오피스·개발도구 목록과 tmux 키 바인딩은 보편 필수가 아니므로 최소 계정에 자동 편입하지 않는다. Git을 켜더라도 이름·메일·인증은 사용자 선택이다. 공통 앱 묶음은 실제 두 번째 소비자가 생겼을 때 별도 opt-in으로 설계한다.
- **동기화 중지**: 기존 서비스는 주 운영자에게 결속돼 있다. 새 계정을 추가한다고 중지·이전하지 않는다. 기기 인계 시에는 서비스와 다른 기기 간 삭제 전파를 먼저 검토하고 별도 결정한다.
- **별도 기기 출력과 교체**: 포크의 별도 출력은 추가 계정 구현과 다른 선택이다. 실제 프로필 생성이나 기존 운영자 제거는 여기서 하지 않는다. 옛 계정의 임시 병존은 복구 수단일 수 있지만 권한·데이터 잔존도 함께 검토해야 한다.
- **인증·데이터·복구**: 자격증명을 복사하지 않고 백업과 복원 가능성을 검증한다. 선언적 계정 변경이 홈 파일·UID 소유물·이전 세대까지 지우거나 격리한다고 가정하지 않는다.

평가만 실행: `nix eval --impure --json --file tests/additional-users.nix` (빌드·활성화 없음). 예시는 최소 계정을 추가한 ThinkPad 설정을 메모리에서만 구성한다.
